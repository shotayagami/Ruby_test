# Rails 第7章: 認証と認可

Webアプリケーションでは「誰であるか」を確かめる認証と、「何をしてよいか」を判断する認可が欠かせません。本章ではセッションベースの自作認証から、Rails 8標準の認証ジェネレータ、Devise、Pundit/CanCanCanによる認可、そしてRailsが標準装備するセキュリティ機構までを実務的にまとめます。

## 1. 認証と認可の違い

「認証」と「認可」は混同されがちですが、担当する責務がまったく異なります。

| 項目 | 認証 (Authentication) | 認可 (Authorization) |
| --- | --- | --- |
| 問い | 「あなたは誰か？」 | 「あなたは何をしてよいか？」 |
| 目的 | 本人性の確認 | 権限（アクセス範囲）の制御 |
| 実行順序 | 先に行う | 認証の後に行う |
| 例 | メールアドレスとパスワードでログイン | 管理者だけが記事を削除できる |
| 代表gem | Devise, 自作 (`has_secure_password`) | Pundit, CanCanCan, 自作 |

処理の流れとしては、まず認証でユーザーを特定し（`current_user` を確定させ）、次に認可でそのユーザーが操作対象のリソースに対して権限を持つかを判定します。認証を通過しても認可で拒否されることは普通に起こります（例: ログイン済みだが他人の投稿は編集できない）。

```ruby
# 認証: リクエストの主体を特定する
before_action :require_login          # ログインしていなければ弾く

# 認可: 特定できた主体が操作を許されるか判定する
before_action :require_admin, only: [:destroy]
```

## 2. セッションベース認証の基礎

HTTPはステートレスなプロトコルなので、リクエストをまたいで「ログイン状態」を保持するにはセッションを使います。Railsのセッションは既定でCookieに保存され、`session` ハッシュを通じて読み書きします。ログイン時にユーザーIDをセッションへ格納し、以降のリクエストでそのIDを頼りにユーザーを復元するのが基本形です。

```ruby
# ログイン時: ユーザーIDをセッションに保存する
session[:user_id] = user.id

# 以降のリクエスト: セッションからユーザーを復元する
User.find_by(id: session[:user_id])

# ログアウト時: セッションを破棄する
session.delete(:user_id)
reset_session   # セッション全体を作り直す（推奨）
```

### ログイン/ログアウトの流れ（ASCII図）

```text
   ブラウザ                          Rails サーバー
     |                                    |
     |  1. POST /login (email, password)  |
     |----------------------------------->|
     |                                    |  User.find_by(email)
     |                                    |  user.authenticate(password)
     |                                    |  session[:user_id] = user.id
     |  2. Set-Cookie: _app_session=...   |
     |<-----------------------------------|
     |                                    |
     |  3. GET /articles                  |
     |     Cookie: _app_session=...       |
     |----------------------------------->|
     |                                    |  current_user =
     |                                    |    User.find_by(id: session[:user_id])
     |  4. 200 OK (ログイン済みビュー)     |
     |<-----------------------------------|
     |                                    |
     |  5. DELETE /logout                 |
     |----------------------------------->|
     |                                    |  reset_session
     |  6. Cookie 破棄 → 未ログイン状態    |
     |<-----------------------------------|
     |                                    |
```

RailsのセッションCookieは署名（および暗号化）されており、改ざんするとサーバー側で検証に失敗します。したがってクライアントが `user_id` を勝手に書き換えて他人になりすますことはできません。ただしCookie自体が盗まれるとセッションを乗っ取られるため、後述の `force_ssl` やセキュアCookieが重要になります。

## 3. has_secure_passwordによる自作認証

Railsは `has_secure_password` というマクロを標準で提供しており、これと `bcrypt` gemを組み合わせるだけで安全なパスワード認証を自作できます。パスワードは平文で保存せず、ハッシュ化して `password_digest` カラムに格納します。

### bcryptの導入とモデル

```ruby
# Gemfile（Rails新規作成時はコメントアウトされているので有効化する）
gem "bcrypt", "~> 3.1.7"
```

```bash
# password_digest カラムを持つ users テーブルを用意する
bin/rails generate model User email:string password_digest:string
bin/rails db:migrate
```

```ruby
# app/models/user.rb
class User < ApplicationRecord
  # password_digest カラムがあれば has_secure_password が有効になる
  has_secure_password

  # メールアドレスの正規化とバリデーション
  normalizes :email, with: ->(email) { email.strip.downcase }
  validates :email, presence: true, uniqueness: true,
                    format: { with: URI::MailTo::EMAIL_REGEXP }
end
```

`has_secure_password` を書くと、モデルに以下が自動で追加されます。

| 追加される機能 | 説明 |
| --- | --- |
| `password=` / `password` | 仮想属性。代入するとbcryptでハッシュ化して `password_digest` に保存 |
| `password_confirmation` | 確認用の仮想属性。一致バリデーションが働く |
| `authenticate(pw)` | パスワードが正しければ自身を、誤りなら `false` を返す |
| バリデーション | 新規作成時に `password` の存在を検証（最大72バイト制限も含む） |

```ruby
# コンソールでの動作確認
user = User.create(email: "alice@example.com",
                   password: "secret123",
                   password_confirmation: "secret123")

user.password_digest        # => "$2a$12$...."（ハッシュ値。平文は保存されない）
user.authenticate("wrong")  # => false
user.authenticate("secret123") # => #<User id: 1, ...>（正しければ自身を返す）
```

### SessionsControllerでログインを実装する

```ruby
# config/routes.rb
Rails.application.routes.draw do
  resource :session, only: [:new, :create, :destroy]
  resources :users, only: [:new, :create]
end
```

```ruby
# app/controllers/sessions_controller.rb
class SessionsController < ApplicationController
  def new
    # ログインフォームを表示するだけ
  end

  def create
    user = User.find_by(email: params[:email]&.downcase)

    # &. と authenticate を組み合わせ、存在確認とパスワード検証を1行で行う
    if user&.authenticate(params[:password])
      reset_session                    # セッション固定攻撃対策
      session[:user_id] = user.id
      redirect_to root_path, notice: "ログインしました"
    else
      # 「メールが違う」「パスワードが違う」を区別しない（情報漏洩を避ける）
      flash.now[:alert] = "メールアドレスまたはパスワードが正しくありません"
      render :new, status: :unprocessable_entity
    end
  end

  def destroy
    reset_session
    redirect_to root_path, notice: "ログアウトしました"
  end
end
```

```erb
<%# app/views/sessions/new.html.erb %>
<h1>ログイン</h1>

<%= form_with url: session_path, method: :post do |f| %>
  <div>
    <%= f.label :email, "メールアドレス" %>
    <%= f.email_field :email %>
  </div>
  <div>
    <%= f.label :password, "パスワード" %>
    <%= f.password_field :password %>
  </div>
  <%= f.submit "ログイン" %>
<% end %>
```

### current_userヘルパーとログイン要求

認証状態をアプリ全体で使い回すため、`ApplicationController` に共通処理を置きます。

```ruby
# app/controllers/application_controller.rb
class ApplicationController < ActionController::Base
  # ビューからも current_user / logged_in? を呼べるようにする
  helper_method :current_user, :logged_in?

  private

  # ||= でリクエスト中の重複クエリを防ぐ（メモ化）
  def current_user
    @current_user ||= User.find_by(id: session[:user_id]) if session[:user_id]
  end

  def logged_in?
    current_user.present?
  end

  # ログインを要求する before_action 用メソッド
  def require_login
    return if logged_in?

    redirect_to new_session_path, alert: "ログインしてください"
  end
end
```

```ruby
# app/controllers/articles_controller.rb
class ArticlesController < ApplicationController
  # index と show 以外はログイン必須にする
  before_action :require_login, except: [:index, :show]

  def new
    @article = current_user.articles.build
  end

  # ...
end
```

```erb
<%# ビューでの分岐 %>
<% if logged_in? %>
  <span><%= current_user.email %> でログイン中</span>
  <%= button_to "ログアウト", session_path, method: :delete %>
<% else %>
  <%= link_to "ログイン", new_session_path %>
<% end %>
```

## 4. Rails 8標準の認証ジェネレータ

Rails 8では、上記のような認証の定型コードを一括生成する `authentication` ジェネレータが標準で追加されました。外部gemに頼らず、フレームワーク組み込みの部品だけで実用的な認証土台を用意できるのが特徴です。

```bash
# 認証に必要な一式を生成する（Rails 8.0以降）
bin/rails generate authentication
```

このジェネレータは概ね次のようなファイルを生成します（生成物はバージョンにより差異があり得ます）。

| 生成物 | 役割 |
| --- | --- |
| `User` モデル | `has_secure_password` を持つユーザー |
| `Session` モデル | ログインセッションをDBに記録（`user_id`, `ip_address`, `user_agent` など） |
| `Current` モデル | `ActiveSupport::CurrentAttributes` によるリクエスト単位の現在ユーザー保持 |
| `Authentication` concern | `require_authentication` などの共通ロジック |
| `SessionsController` | ログイン/ログアウト |
| `PasswordsController` / メーラー | パスワードリセット |
| マイグレーション | `users` と `sessions` テーブル |

Rails 8で追加・強調された点として、確実に言えるのは次のとおりです。

- 生成される認証は `bcrypt` を利用し、`has_secure_password` を土台にしている。
- セッションを単なる `session[:user_id]` ではなく **`Session` モデル（DBレコード）** として管理し、その識別子を署名付きCookieに保存する設計になっている。これによりセッションの一覧・失効管理がしやすい。
- 現在のユーザーは `Current.user` のように `CurrentAttributes` 経由で参照する。
- コントローラには既定で認証が要求され、公開したいアクションは `allow_unauthenticated_access` で個別に解放する、というオプトアウト型の設計になっている。

```ruby
# 生成される Authentication concern の使い方（イメージ）
class ArticlesController < ApplicationController
  # 既定では全アクションで認証が要求される。
  # 公開アクションだけを明示的に解放する。
  allow_unauthenticated_access only: [:index, :show]
end
```

> 補足: ジェネレータが出力するメソッド名やファイル構成の細部はRailsのマイナーバージョンで変わり得ます。正確な生成物は、実際に生成した後の `git diff` や公式ガイド（Securing Rails Applications / リリースノート）で確認してください。ここでは確実な範囲のみを記載しています。

Deviseと比べると、Rails 8ジェネレータは「生成されたコードが自分のアプリの一部になる」ため、挙動を完全に把握・改変できる一方、パスワードリセット以上の機能（確認メール、アカウントロック、OAuth連携など）は自前で追加する必要があります。

## 5. Deviseによる認証

[Devise](https://github.com/heartcombo/devise) は最も広く使われている認証gemで、ユーザー登録・ログイン・パスワードリセット・メール確認・アカウントロックなどをモジュール単位で提供します。定番機能をまとめて手に入れたい場合の第一候補です。

### 最小セットアップ手順

```ruby
# Gemfile
gem "devise"
```

```bash
bundle install

# 初期化（設定ファイルとロケールを生成）
bin/rails generate devise:install

# User モデルに Devise を組み込む
bin/rails generate devise User
bin/rails db:migrate
```

```ruby
# app/models/user.rb（生成される）
class User < ApplicationRecord
  # 利用するモジュールを列挙する
  devise :database_authenticatable, :registerable,
         :recoverable, :rememberable, :validatable
end
```

Deviseを導入すると、`authenticate_user!`（ログイン要求）、`current_user`、`user_signed_in?` などのヘルパーがコントローラ／ビューで自動的に使えるようになります。

```ruby
class ArticlesController < ApplicationController
  # Deviseが提供する認証フィルタ
  before_action :authenticate_user!
end
```

```erb
<% if user_signed_in? %>
  <%= current_user.email %>
  <%= link_to "ログアウト", destroy_user_session_path, data: { turbo_method: :delete } %>
<% else %>
  <%= link_to "ログイン", new_user_session_path %>
<% end %>
```

Deviseはビューのカスタマイズ（`bin/rails generate devise:views`）、確認メール（`:confirmable`）、OAuth（`omniauth`連携）など多くの拡張ポイントを持ちます。設定・カスタマイズ・各モジュールの詳細については別資料 [`../gems/devise.md`](../gems/devise.md) を参照してください。

## 6. 認可（Authorization）

認証で `current_user` が確定したら、次はそのユーザーが操作を許されているかを判定します。まずは外部gemなしの素朴な実装から見ていきます。

### 自作の権限チェック

小規模なアプリなら、モデルにロール（役割）カラムを持たせて `before_action` で判定するだけで十分なことも多いです。

```ruby
# enum でロールを定義する
class User < ApplicationRecord
  has_secure_password
  enum :role, { member: 0, editor: 1, admin: 2 }
end
```

```ruby
class ArticlesController < ApplicationController
  before_action :require_login
  before_action :set_article, only: [:edit, :update, :destroy]
  before_action :require_owner_or_admin, only: [:edit, :update, :destroy]

  private

  def require_owner_or_admin
    # 投稿者本人か管理者だけが編集・削除できる
    return if @article.user == current_user || current_user.admin?

    redirect_to articles_path, alert: "権限がありません"
  end
end
```

素朴な方法は分かりやすい反面、権限ロジックがコントローラに散らばりやすく、コントローラとビューで判定が二重化しがちです。ルールが増えてきたら専用のライブラリに寄せると保守性が上がります。

### Pundit と CanCanCan の比較

| 観点 | Pundit | CanCanCan |
| --- | --- | --- |
| 設計思想 | リソースごとに **Policyクラス** を書く（分散型） | 1つの **Abilityクラス** に全権限を集約（集中型） |
| 権限の記述場所 | `app/policies/*_policy.rb` | `app/models/ability.rb` |
| 記述スタイル | 素のRubyメソッド（明示的） | DSL（`can`/`cannot`） |
| 権限判定 | `authorize @article` | `authorize! :update, @article` |
| スコープ絞り込み | Policy Scope | `accessible_by` |
| 向いている規模 | 中〜大規模、ルールが複雑な場合 | 小〜中規模、権限を一望したい場合 |
| 学習コスト | 低め（普通のRubyに近い） | DSLを覚える必要がある |

#### Pundit の例

```ruby
# Gemfile
gem "pundit"
```

```ruby
# app/policies/article_policy.rb
class ArticlePolicy < ApplicationPolicy
  # update? が true を返せば更新を許可する
  def update?
    record.user == user || user.admin?
  end

  def destroy?
    user.admin?
  end
end
```

```ruby
class ArticlesController < ApplicationController
  def update
    @article = Article.find(params[:id])
    authorize @article        # ArticlePolicy#update? を自動で呼ぶ
    # 権限がなければ Pundit::NotAuthorizedError が発生する
    @article.update!(article_params)
    redirect_to @article
  end
end
```

#### CanCanCan の例

```ruby
# Gemfile
gem "cancancan"
```

```ruby
# app/models/ability.rb
class Ability
  include CanCan::Ability

  def initialize(user)
    user ||= User.new           # 未ログインはゲスト扱い
    if user.admin?
      can :manage, :all         # 管理者は全操作可能
    else
      can :read, Article        # 誰でも閲覧可
      can :update, Article, user_id: user.id  # 自分の投稿だけ更新可
    end
  end
end
```

```ruby
class ArticlesController < ApplicationController
  def update
    @article = Article.find(params[:id])
    authorize! :update, @article  # 権限がなければ CanCan::AccessDenied
    @article.update!(article_params)
    redirect_to @article
  end
end
```

いずれのgemも「権限判定を1か所に集約し、コントローラ／ビューから同じルールを参照する」ことで、認可ロジックの重複と抜け漏れを防ぎます。認可エラーは `rescue_from` で捕捉し、403ページやリダイレクトに変換するのが定石です。

```ruby
# Pundit の場合
rescue_from Pundit::NotAuthorizedError do
  redirect_to root_path, alert: "権限がありません"
end
```

## 7. Railsのセキュリティ機構

Railsは「安全な既定値（secure by default）」を重視しており、多くの攻撃対策が最初から有効になっています。主要な機構を整理します。

| 脅威 | 対策機構 | 既定の状態 |
| --- | --- | --- |
| CSRF | 認証トークン検証 | 有効 |
| Mass Assignment | Strong Parameters | 有効（必須） |
| SQLインジェクション | プレースホルダ／バインド変数 | 正しく使えば安全 |
| XSS | ERBの自動エスケープ | 有効 |
| 秘密情報の漏洩 | credentials + master.key | 有効 |
| 通信の盗聴 | force_ssl / セキュアCookie | 本番で推奨 |

### CSRF対策

CSRF（クロスサイトリクエストフォージェリ）は、ログイン済みユーザーに意図しないリクエストを送らせる攻撃です。Railsは `ApplicationController` の `protect_from_forgery`（現行では既定で有効）により、`form_with` が埋め込む認証トークン（authenticity_token）を検証して防ぎます。

```ruby
class ApplicationController < ActionController::Base
  # 現行Railsでは既定で有効。トークン不一致時の挙動を指定できる。
  protect_from_forgery with: :exception
end
```

```erb
<%# form_with は hidden な authenticity_token を自動で埋め込む %>
<%= form_with model: @article do |f| %>
  <%= f.text_field :title %>
  <%= f.submit %>
<% end %>
```

GETは状態を変更しないため検証対象外です。状態を変える操作は必ずPOST/PATCH/DELETEにするのが原則です。JavaScriptからAPIを叩く場合は `<meta name="csrf-token">` の値をヘッダに載せます。

### Strong Parameters による Mass Assignment 対策

`params` をそのままモデルに渡すと、フォームにない属性（例: `admin`）まで書き換えられてしまう恐れがあります（Mass Assignment脆弱性）。`permit` で許可した属性だけを通します。

```ruby
private

def article_params
  # title と body だけを許可する。role や user_id は通さない。
  params.require(:article).permit(:title, :body)
end
```

### SQLインジェクション対策

文字列を直接埋め込むと危険です。プレースホルダ（`?`）や名前付きバインド、ハッシュ条件を使えばActive Recordが自動でエスケープします。

```ruby
# 危険: ユーザー入力を文字列連結している（絶対に避ける）
User.where("email = '#{params[:email]}'")

# 安全: プレースホルダを使う
User.where("email = ?", params[:email])

# 安全: ハッシュ条件（最も推奨）
User.where(email: params[:email])
```

### XSS対策

ERBの `<%= %>` は出力を自動でHTMLエスケープするため、既定でXSSに強い設計です。エスケープを無効化する `html_safe` や `raw` はユーザー入力に対して使ってはいけません。ユーザー由来のHTMLを表示する必要がある場合は `sanitize` を通します。

```erb
<%# 安全: 自動エスケープされる %>
<%= @comment.body %>

<%# 危険: エスケープを無効化。ユーザー入力には使わない %>
<%= @comment.body.html_safe %>

<%# 必要な場合: 許可タグだけ残して無害化する %>
<%= sanitize @comment.body, tags: %w[strong em a], attributes: %w[href] %>
```

### credentials と master.key による秘密情報管理

APIキーやパスワードなどの秘密情報は、暗号化された `config/credentials.yml.enc` に保存します。復号鍵は `config/master.key`（または環境変数 `RAILS_MASTER_KEY`）で、`master.key` は `.gitignore` 済みでリポジトリにコミットしません。

```bash
# 暗号化された credentials を編集する（既定のエディタが開く）
bin/rails credentials:edit

# 環境ごとに分ける場合
bin/rails credentials:edit --environment production
```

```yaml
# credentials:edit で開かれる中身（平文で編集し、保存時に暗号化される）
secret_key_base: xxxxxxxx
aws:
  access_key_id: AKIAxxxx
  secret_access_key: yyyyyyyy
```

```ruby
# コード中からの参照
Rails.application.credentials.aws[:access_key_id]
Rails.application.credentials.dig(:aws, :secret_access_key)
```

### force_ssl とセキュアCookie

本番環境ではHTTPSを強制し、Cookieが盗聴されないようにします。

```ruby
# config/environments/production.rb
config.force_ssl = true
# これにより HTTP は HTTPS にリダイレクトされ、
# セッションCookieに secure 属性が付き、HSTSヘッダも送られる。
```

`force_ssl` を有効にするとセッションCookieに `secure` 属性（HTTPS接続時のみ送信）が自動付与されます。加えてセッションCookieには既定で `HttpOnly` 属性が付き、JavaScriptからの読み取りを防いでXSS経由のCookie窃取リスクを下げます。

## 8. Brakemanによるセキュリティスキャン

[Brakeman](https://brakemanscanner.org/) はRails専用の静的セキュリティ解析ツールです。アプリを実行せずソースコードを解析し、SQLインジェクション、XSS、Mass Assignment、危険なリダイレクトなどの潜在的脆弱性を検出します。Rails 8では新規アプリのGemfileに標準で含まれます。

```ruby
# Gemfile
gem "brakeman", require: false
```

```bash
# スキャンを実行する
bin/brakeman

# HTMLレポートとして出力する
bin/brakeman -o report.html

# 確認済みの警告を除外して差分だけ見る
bin/brakeman -I   # 対話的に無視リスト(brakeman.ignore)を作成
```

CIに組み込み、新たな警告が出たらビルドを失敗させる運用が一般的です。RuboCopのセキュリティ系cop（`rubocop-rails` 等）と併用すると、コーディング段階から脆弱性の混入を抑えられます。

## 9. HTTP BasicとToken認証

ブラウザUIを介さないAPIや、社内向けの簡易保護には、HTTP標準の認証方式が手軽です。Action Controllerがヘルパーを提供しています。

### HTTP Basic認証

```ruby
class AdminController < ApplicationController
  # ブラウザにID/パスワードの入力ダイアログを出す
  http_basic_authenticate_with name: "admin", password: "secret"
end
```

```ruby
# 手動で判定する場合
class ReportsController < ApplicationController
  before_action :authenticate

  private

  def authenticate
    authenticate_or_request_with_http_basic do |username, password|
      # 戻り値が truthy なら認証成功
      username == "admin" && ActiveSupport::SecurityUtils.secure_compare(password, ENV["ADMIN_PASSWORD"])
    end
  end
end
```

Basic認証はIDとパスワードをリクエストごとに送るため、必ずHTTPS上で使います。

### Token認証

APIではAuthorizationヘッダにトークンを載せる方式がよく使われます。

```ruby
class Api::BaseController < ActionController::API
  before_action :authenticate

  private

  def authenticate
    # Authorization: Token token="abc123" を検証する
    authenticate_or_request_with_http_token do |token, _options|
      # secure_compare でタイミング攻撃を避けつつ照合する
      @current_api_user = ApiKey.find_by(token: token)&.user
      @current_api_user.present?
    end
  end
end
```

これらの方式は簡易で強力ですが、トークン失効やスコープ管理などの高度な要件がある場合は、専用の認可基盤（OAuth 2.0 / JWT など）の採用を検討します。
