## 1. Active Job（非同期ジョブ）

Active Jobは「バックグラウンドで実行したい処理」を統一APIで書くための仕組みです。メール送信・画像変換・外部API呼び出しなど、レスポンスを遅らせたくない処理をキューに積んで後で実行します。バックエンド（キューアダプタ）を差し替えても、ジョブのコードはそのまま使えるのが特徴です。

### ジョブの生成

```bash
# app/jobs/guests_cleanup_job.rb が生成される
rails generate job guests_cleanup
```

```ruby
# app/jobs/guests_cleanup_job.rb
class GuestsCleanupJob < ApplicationJob
  # キュー名を指定（省略時は :default）
  queue_as :default

  # 引数はジョブに渡す値。シリアライズ可能なものにする
  def perform(*guests)
    # 時間のかかる処理をここに書く
    Guest.where(active: false).delete_all
  end
end
```

### perform_later と perform_now

```ruby
# 非同期実行（キューに積む。すぐ制御が返る）
GuestsCleanupJob.perform_later

# 同期実行（その場で実行。テストやrake taskで便利）
GuestsCleanupJob.perform_now

# 引数を渡す
NotifyJob.perform_later(user, message: "こんにちは")

# 実行時刻を指定
CleanupJob.set(wait: 1.week).perform_later          # 1週間後
CleanupJob.set(wait_until: Date.tomorrow.noon).perform_later
CleanupJob.set(queue: :low_priority).perform_later   # キューを上書き
```

**注意:** 引数にActive Recordオブジェクトを渡すと、GlobalIDで「idだけ」がシリアライズされ、実行時にDBから再取得されます。実行までにレコードが削除されると `ActiveJob::DeserializationError` になります。

**🎯 Django:** 非同期処理は Celery が定番です。`shared_task` でタスクを定義し、`.delay()` / `.apply_async()` でキューに積みます。

```python
# tasks.py（Celery）
from celery import shared_task

@shared_task
def guests_cleanup():
    Guest.objects.filter(active=False).delete()

guests_cleanup.delay()                      # perform_later 相当
guests_cleanup.apply_async(countdown=3600)  # set(wait: 1.hour) 相当
```

CeleryはブローカーとしてRedis/RabbitMQが必須で、Solid QueueのようなDB標準キューはありません（DBで完結させたいなら Django-Q や Django-RQ）。同期実行（perform_now 相当）はタスク関数を直接呼ぶだけです。

### キューアダプタ

ジョブを実際に処理する「バックエンド」を選びます。設定は `config/application.rb` または各環境ファイルで行います。

```ruby
# config/environments/production.rb
# Rails 8 のデフォルト（DBベース、Redis不要）
config.active_job.queue_adapter = :solid_queue

# Sidekiq を使う場合
# config.active_job.queue_adapter = :sidekiq
```

| アダプタ | 永続化 | 特徴 |
| --- | --- | --- |
| `:async` | なし（プロセス内メモリ） | 開発用。再起動でジョブ消失。本番厳禁 |
| `:test` | なし | テスト用。ジョブをキャプチャして検証 |
| `:solid_queue` | DB（RDB） | **Rails 8標準**。Redis不要でスケール可能 |
| `:sidekiq` | Redis | 高スループット、実績豊富。要Redis |
| `:delayed_job` / `:resque` | DB / Redis | 旧来のアダプタ |

**Solid Queue（Rails 8標準）** はRDBのテーブルをキューとして使うため、追加のミドルウェア（Redis等）が不要です。専用ワーカープロセスをPumaとは別に起動します。

```bash
# Solid Queue のセットアップ（テーブル追加）
bin/rails solid_queue:install
bin/rails db:migrate

# ワーカーの起動
bin/jobs start
```

Sidekiqの詳細な導入・設定・監視については別資料を参照してください → [`../gems/sidekiq.md`](../gems/sidekiq.md)

### コールバックと例外処理

```ruby
class RiskyJob < ApplicationJob
  # 特定の例外はリトライ（回数と待機を指定）
  retry_on Net::OpenTimeout, wait: 5.seconds, attempts: 3

  # このエラーはリトライせず破棄する
  discard_on ActiveJob::DeserializationError

  around_perform do |job, block|
    block.call
  ensure
    # 後処理（ログ記録など）
  end

  def perform(url)
    # ...
  end
end
```

## 2. Action Mailer（メール送信）

Action Mailerはメール送信を担当します。コントローラ／ビューとよく似た構造で、メーラクラスのメソッドが「アクション」、`app/views/xxx_mailer/` のテンプレートが本文になります。

### メーラの生成

```bash
rails generate mailer UserMailer welcome
# app/mailers/user_mailer.rb
# app/views/user_mailer/welcome.html.erb / welcome.text.erb
```

```ruby
# app/mailers/user_mailer.rb
class UserMailer < ApplicationMailer
  default from: "no-reply@example.com"   # 全メソッド共通の送信元

  def welcome(user)
    @user = user                         # ビューで使うインスタンス変数
    @url  = login_url
    mail(to: @user.email, subject: "ようこそ")
  end
end
```

### ビュー（HTML / テキスト）

HTMLとテキストの両方を用意するとマルチパートメールになります（受信側の環境に応じて表示）。

```erb
<%# app/views/user_mailer/welcome.html.erb %>
<h1><%= @user.name %>さん、ようこそ</h1>
<p><%= link_to "ログイン", @url %></p>
```

```erb
<%# app/views/user_mailer/welcome.text.erb %>
<%= @user.name %>さん、ようこそ
ログイン: <%= @url %>
```

### 送信: deliver_later と deliver_now

```ruby
# Active Job経由で非同期送信（推奨。リクエストを待たせない）
UserMailer.welcome(@user).deliver_later

# その場で同期送信
UserMailer.welcome(@user).deliver_now

# 送信を遅らせる
UserMailer.welcome(@user).deliver_later(wait: 1.hour)
```

`deliver_later` は内部で `ActionMailer::MailDeliveryJob` をキューに積むため、Active Jobのアダプタ（Solid Queue / Sidekiq等）が動いている必要があります。

**🎯 Django:** メールは `django.core.mail` で送ります。メーラクラスはなく、関数から直接送信します。

```python
# django.core.mail
from django.core.mail import send_mail, EmailMultiAlternatives
from django.template.loader import render_to_string

# シンプルな1通
send_mail("ようこそ", "本文", "no-reply@example.com", [user.email])

# テンプレート + HTML/テキストのマルチパート（welcome.html / .txt 相当）
text = render_to_string("email/welcome.txt", {"user": user})
html = render_to_string("email/welcome.html", {"user": user})
msg = EmailMultiAlternatives("ようこそ", text, "no-reply@example.com", [user.email])
msg.attach_alternative(html, "text/html")
msg.send()
```

`deliver_later` に相当する仕組みは標準になく、非同期送信はCeleryタスクの中で `send()` を呼びます。

### SMTP設定

```ruby
# config/environments/production.rb
config.action_mailer.delivery_method = :smtp
config.action_mailer.smtp_settings = {
  address:              "smtp.sendgrid.net",
  port:                 587,
  user_name:            "apikey",
  password:             Rails.application.credentials.dig(:sendgrid, :api_key),
  authentication:       :plain,
  enable_starttls_auto: true
}
# URLヘルパー（*_url）を使うためホスト名が必須
config.action_mailer.default_url_options = { host: "example.com" }
```

**🎯 Django:** SMTPは `settings.py` の `EMAIL_*` で設定します。

```python
# settings.py
EMAIL_BACKEND = "django.core.mail.backends.smtp.EmailBackend"
EMAIL_HOST = "smtp.sendgrid.net"
EMAIL_PORT = 587
EMAIL_HOST_USER = "apikey"
EMAIL_HOST_PASSWORD = os.environ["SENDGRID_API_KEY"]
EMAIL_USE_TLS = True
```

開発では `console.EmailBackend`（メールを標準出力へ表示）が letter_opener 的な確認手段になります。

| delivery_method | 用途 |
| --- | --- |
| `:smtp` | 本番。外部SMTPサーバ経由 |
| `:test` | テスト。`ActionMailer::Base.deliveries` 配列に蓄積 |
| `:letter_opener`（gem） | 開発。送信の代わりにブラウザで確認 |

### プレビュー

開発中にブラウザでメール文面を確認できます。

```ruby
# test/mailers/previews/user_mailer_preview.rb
class UserMailerPreview < ActionMailer::Preview
  def welcome
    UserMailer.welcome(User.first)
  end
end
```

`http://localhost:3000/rails/mailers/user_mailer/welcome` で確認できます。

## 3. Active Storage（ファイルアップロード）

Active Storageはファイル添付（画像・PDF等）を扱う標準機能です。ローカルディスクやS3などのクラウドストレージにアップロードでき、モデルに関連づけて管理します。

### セットアップ

```bash
# active_storage_blobs / attachments / variant_records テーブルを追加
rails active_storage:install
rails db:migrate
```

### モデルへの関連づけ

```ruby
class User < ApplicationRecord
  has_one_attached :avatar        # 1ファイル
end

class Post < ApplicationRecord
  has_many_attached :images       # 複数ファイル
end
```

**🎯 Django:** ファイルはモデルの `FileField` / `ImageField` で扱います。

```python
# models.py
class User(models.Model):
    avatar = models.ImageField(upload_to="avatars/", blank=True)

class Post(models.Model):
    image = models.ImageField(upload_to="posts/", blank=True)
```

`has_many_attached` のような「1フィールドで複数添付」はなく、複数ファイルは別モデル + ForeignKey で表します。バリアント（リサイズ）も標準にはなく、easy-thumbnails / sorl-thumbnail 等を使います。

### 添付と保存

```ruby
# フォームから（params[:avatar] はアップロードされたファイル）
@user.avatar.attach(params[:avatar])

# ファイルから直接
@user.avatar.attach(io: File.open("logo.png"), filename: "logo.png", content_type: "image/png")

@user.avatar.attached?   # 添付有無を確認 => true / false
@user.avatar.purge       # 削除（同期）
@user.avatar.purge_later # 削除（非同期）
```

```erb
<%# フォーム側 %>
<%= form_with model: @user do |f| %>
  <%= f.file_field :avatar %>
  <%= f.submit %>
<% end %>
```

```ruby
# ストロングパラメータで許可
params.require(:user).permit(:name, :avatar)
```

### ビューでの表示とバリアント

`variant` で画像をリサイズ・加工できます（`image_processing` gem と ImageMagick / libvips が必要）。

```erb
<%# 元画像 %>
<%= image_tag @user.avatar if @user.avatar.attached? %>

<%# 100x100 にリサイズしたバリアント %>
<%= image_tag @user.avatar.variant(resize_to_limit: [100, 100]) %>

<%# ダウンロードリンク %>
<%= link_to "PDF", rails_blob_path(@post.document, disposition: "attachment") %>
```

### 外部ストレージ（S3互換）

保存先は `config/storage.yml` で「サービス」として定義し、環境ごとに選択します。

```yaml
# config/storage.yml
local:
  service: Disk
  root: <%= Rails.root.join("storage") %>

amazon:
  service: S3
  access_key_id: <%= Rails.application.credentials.dig(:aws, :access_key_id) %>
  secret_access_key: <%= Rails.application.credentials.dig(:aws, :secret_access_key) %>
  region: ap-northeast-1
  bucket: my-app-bucket
```

```ruby
# config/environments/production.rb
config.active_storage.service = :amazon   # storage.yml のキー名
```

**🎯 Django:** S3などの外部ストレージは django-storages（+ boto3）で切り替えます。

```python
# settings.py
STORAGES = {
    "default": {
        "BACKEND": "storages.backends.s3.S3Storage",
        "OPTIONS": {"bucket_name": "my-app-bucket", "region_name": "ap-northeast-1"},
    },
}
```

storage.yml のようなサービス定義ファイルではなく、`settings.py` の `STORAGES`（Django 4.2+）で保存先を指定します。

Cloudflare R2（S3互換）への接続手順・エンドポイント設定は別資料を参照してください → [`../gems/cloudflare-r2.md`](../gems/cloudflare-r2.md)

## 4. Action Cable と Turbo Streams

### Action Cable（WebSocket）

Action CableはWebSocketを使ったリアルタイム通信（チャット、通知、進捗表示など）を実現します。サーバとクライアントが接続を維持し、双方向にメッセージを送れます。

```bash
rails generate channel Chat
# app/channels/chat_channel.rb
# app/javascript/channels/chat_channel.js
```

```ruby
# app/channels/chat_channel.rb
class ChatChannel < ApplicationCable::Channel
  # クライアントが購読したときに呼ばれる
  def subscribed
    stream_from "chat_room_#{params[:room_id]}"
  end

  def unsubscribed
    # 購読解除時のクリーンアップ
  end
end
```

```ruby
# サーバ側からブロードキャスト（コントローラやジョブから）
ActionCable.server.broadcast(
  "chat_room_#{room.id}",
  { body: message.body, user: message.user_name }
)
```

**🎯 Django:** WebSocketは Django Channels（ASGI）で実装します。Consumer が Channel に、group が stream に対応します。

```python
# consumers.py
from channels.generic.websocket import AsyncJsonWebsocketConsumer

class ChatConsumer(AsyncJsonWebsocketConsumer):
    async def connect(self):
        self.room = self.scope["url_route"]["kwargs"]["room_id"]
        await self.channel_layer.group_add(f"chat_{self.room}", self.channel_name)
        await self.accept()

    async def chat_message(self, event):   # group_send の type= と対応
        await self.send_json(event["data"])
```

```python
# サーバ側からブロードキャスト
from asgiref.sync import async_to_sync
from channels.layers import get_channel_layer

async_to_sync(get_channel_layer().group_send)(
    f"chat_{room.id}", {"type": "chat_message", "data": {"body": message.body}}
)
```

ChannelsはASGIサーバ（daphne / uvicorn）で動かし、channel layer のバックエンドにRedis（本番）またはInMemoryを使います。Turbo Streams / Hotwire に相当する標準機能はありません。

**Rails 8の Solid Cable:** 従来Action Cableのpub/subには本番でRedisが必要でしたが、Rails 8標準の **Solid Cable** はRDBを使うためRedis不要です。設定は `config/cable.yml` で行います。

```yaml
# config/cable.yml
production:
  adapter: solid_cable      # Rails 8標準（Redis不要）
  # adapter: redis          # 従来型
  # url: <%= ENV["REDIS_URL"] %>
```

### Turbo Streams（Hotwire）

多くの「リアルタイムなUI更新」は、生のAction Cableを書かずに **Turbo Streams**（Hotwireの一部、Rails標準）で実現できます。モデルの更新をトリガに、HTMLの断片をWebSocket経由でブラウザへ送り、DOMを差し替えます。

```erb
<%# ビュー: この要素をストリームで購読 %>
<%= turbo_stream_from "messages" %>
<div id="messages">
  <%= render @messages %>
</div>
```

```ruby
# モデル: 作成時に自動でブロードキャスト
class Message < ApplicationRecord
  belongs_to :room
  # messages ストリームへ、_message パーシャルを append する
  broadcasts_to ->(message) { "messages" }
end
```

JavaScriptをほとんど書かずに、フォーム送信やモデル更新に応じたリアルタイムUIが作れます。

## 5. Action Text（リッチテキスト）

Action Textはリッチテキスト編集（太字・リスト・画像埋め込み等）を提供します。エディタには Trix を使い、埋め込み画像はActive Storageで保存されます。

```bash
# 依存（Active Storage含む）をインストール
rails action_text:install
rails db:migrate
```

```ruby
class Article < ApplicationRecord
  has_rich_text :content    # rich_text_content として保存される
end
```

```erb
<%# フォーム %>
<%= form_with model: @article do |f| %>
  <%= f.rich_text_area :content %>
  <%= f.submit %>
<% end %>

<%# 表示（サニタイズ済みHTMLがそのまま出力される） %>
<%= @article.content %>
```

ストロングパラメータでは `:content` を許可します。埋め込み画像を使う場合はActive Storageのストレージ設定が必要です。

## 6. APIモード

JSON APIサーバとしてRailsを使う場合、ビューやアセットなど不要なミドルウェアを省いた軽量構成で始められます。

### API専用アプリの作成

```bash
rails new my_api --api
```

APIモードでは、コントローラの基底クラスが `ActionController::Base` ではなく `ActionController::API` になります（Cookie・Flash・ビューレンダリング等が外れ、軽量）。

```ruby
class Api::V1::UsersController < ActionController::API
  def index
    users = User.all
    render json: users              # 配列を自動でJSON化
  end

  def show
    user = User.find(params[:id])
    render json: user, status: :ok  # ステータスは明示できる
  end

  def create
    user = User.new(user_params)
    if user.save
      render json: user, status: :created
    else
      render json: { errors: user.errors.full_messages }, status: :unprocessable_entity
    end
  end
end
```

**🎯 Django:** JSON APIは Django REST Framework（DRF）が定番です。ViewSet + Router でCRUDとルーティングをまとめて生成します。

```python
# views.py + urls.py
from rest_framework import viewsets
from rest_framework.routers import DefaultRouter

class UserViewSet(viewsets.ModelViewSet):
    queryset = User.objects.all()
    serializer_class = UserSerializer

router = DefaultRouter()
router.register("users", UserViewSet)   # index / show / create 等を自動ルーティング
```

ViewSet + Router は Rails の `resources :users` に近く、標準アクションとルートを一括生成します。

### レスポンスの整形（jbuilder / シリアライザ）

`render json:` は手軽ですが、出力する属性を制御したいときはテンプレートやシリアライザを使います。

```ruby
# jbuilder（Railsに同梱。ビューでJSONを組み立てる）
# app/views/api/v1/users/show.json.jbuilder
json.id    @user.id
json.name  @user.name
json.posts @user.posts do |post|
  json.title post.title
end
```

**🎯 Django:** 出力属性の制御は DRF の Serializer で宣言します（jbuilder に相当）。

```python
# serializers.py
from rest_framework import serializers

class UserSerializer(serializers.ModelSerializer):
    posts = PostSerializer(many=True, read_only=True)

    class Meta:
        model = User
        fields = ["id", "name", "posts"]
```

| 方式 | 特徴 |
| --- | --- |
| `render json:` + `as_json` | 手軽。小規模向け。モデルで `as_json` をオーバーライド可能 |
| jbuilder | ビュー層でJSONを宣言的に構築。Rails同梱 |
| active_model_serializers / blueprinter（gem） | シリアライザをクラスで管理。中〜大規模向け |
| jsonapi-serializer（gem） | JSON:API仕様に準拠 |

### CORS

ブラウザの別オリジン（SPA等）からアクセスさせるにはCORS設定が必要です。`rack-cors` gemを使います。

```ruby
# Gemfile
gem "rack-cors"
```

```ruby
# config/initializers/cors.rb
Rails.application.config.middleware.insert_before 0, Rack::Cors do
  allow do
    origins "https://app.example.com"      # 許可するオリジン
    resource "*", headers: :any, methods: [:get, :post, :put, :patch, :delete, :options]
  end
end
```

**🎯 Django:** CORSは django-cors-headers で設定します（rack-cors に相当）。

```python
# settings.py
INSTALLED_APPS += ["corsheaders"]
MIDDLEWARE = ["corsheaders.middleware.CorsMiddleware", *MIDDLEWARE]  # なるべく先頭側に置く
CORS_ALLOWED_ORIGINS = ["https://app.example.com"]
```

### トークン認証の指針

- **セッション/CookieはAPIでは基本使わない**（別オリジンSPAやモバイルではトークンが扱いやすい）。
- 単純な用途なら `ActionController::HttpAuthentication::Token`、本格的なものはJWT（`jwt` gem）を利用。
- 認可（ロール制御）は `pundit` / `cancancan` などを併用。
- トークンはHTTPSでのみ送受信し、有効期限と失効の仕組みを持たせる。

```ruby
# シンプルなトークン認証の例
class ApplicationController < ActionController::API
  include ActionController::HttpAuthentication::Token::ControllerMethods

  before_action :authenticate

  private

  def authenticate
    authenticate_or_request_with_http_token do |token, _options|
      @current_user = User.find_by(api_token: token)
    end
  end
end
```

**🎯 Django:** DRFは認証クラスを差し替える方式です。トークン認証やJWTを設定で有効化します。

```python
# settings.py
REST_FRAMEWORK = {
    "DEFAULT_AUTHENTICATION_CLASSES": [
        "rest_framework.authentication.TokenAuthentication",
    ],
}
```

本格的なJWTは djangorestframework-simplejwt、認可（ロール制御）は DRF の permission クラスで行います。

## 7. I18n（国際化）

I18n（internationalization）は、表示文言を言語ごとの辞書ファイルに分離する仕組みです。日本語・英語の切り替えや、日付・数値のロケール別書式に対応できます。

### ロケールファイル

```yaml
# config/locales/ja.yml
ja:
  hello: "こんにちは"
  users:
    greeting: "%{name}さん、ようこそ"     # プレースホルダ
  date:
    formats:
      default: "%Y年%m月%d日"
```

```yaml
# config/locales/en.yml
en:
  hello: "Hello"
  users:
    greeting: "Welcome, %{name}"
```

### 設定

```ruby
# config/application.rb
config.i18n.default_locale = :ja
config.i18n.available_locales = [:ja, :en]
# locales以下のサブフォルダも読み込む
config.i18n.load_path += Dir[Rails.root.join("config", "locales", "**", "*.yml")]
```

### t / l ヘルパー

```erb
<%= t("hello") %>                              <%# => こんにちは %>
<%= t("users.greeting", name: "田中") %>       <%# => 田中さん、ようこそ %>
<%= l(Time.current) %>                          <%# ロケール書式で日時 %>
<%= l(Date.today, format: :long) %>
```

```ruby
# コードからも使える
I18n.t("hello")
I18n.l(Time.current)
```

**🎯 Django:** 文言は辞書YAMLではなく、ソース中の文字列を `gettext`（`_()`）でマークします。

```python
# gettext でマーク
from django.utils.translation import gettext as _

greeting = _("Hello")            # t("hello") 相当
```

> テンプレートでは `{% load i18n %}` と `{% trans "Hello" %}` を使います。

`makemessages` で `.po` を抽出→`compilemessages` で `.mo` にコンパイルします。ロケール切替は `LocaleMiddleware` と `settings.LANGUAGES` / `translation.activate()` で行います。

**遅延ルックアップ:** ビュー内で先頭ドットを使うと、パスをテンプレート位置から補完します。

```erb
<%# app/views/users/show.html.erb 内で %>
<%= t(".title") %>   <%# => users.show.title を参照 %>
```

### ロケールの切り替え

```ruby
class ApplicationController < ActionController::Base
  around_action :switch_locale

  private

  def switch_locale(&action)
    # paramsやAccept-Languageから決定
    locale = params[:locale] || I18n.default_locale
    I18n.with_locale(locale, &action)
  end

  # 生成されるURLにlocaleを引き継ぐ
  def default_url_options
    { locale: I18n.locale }
  end
end
```

モデルの属性名やバリデーションメッセージも `activerecord.attributes.*` / `errors.*` の名前空間で翻訳できます。

## 8. キャッシュ

キャッシュはレンダリング結果や計算結果を保存し、再利用して高速化する仕組みです。開発環境ではデフォルト無効なので、確認するには `rails dev:cache` で有効化します。

### フラグメントキャッシュ

ビューの一部（パーシャル等）をキャッシュします。キーにモデルを渡すと `updated_at` を含むキーが自動生成され、更新時に自動で無効化されます。

```erb
<% @products.each do |product| %>
  <% cache product do %>          <%# product が更新されると自動で失効 %>
    <%= render product %>
  <% end %>
<% end %>
```

### ロシアンドールキャッシュ

キャッシュを入れ子にする手法です。内側が更新されると内側だけ再生成され、外側は再利用されます。`touch: true` で子の更新を親へ伝播させるのがポイントです。

```ruby
class Product < ApplicationRecord
  belongs_to :category, touch: true   # productが更新されるとcategoryのupdated_atも更新
end
```

```erb
<% cache category do %>
  <h2><%= category.name %></h2>
  <% category.products.each do |product| %>
    <% cache product do %>            <%# 内側 %>
      <%= render product %>
    <% end %>
  <% end %>
<% end %>
```

### 低レベルキャッシュ（Rails.cache）

任意の値をキャッシュストアに直接読み書きします。`fetch` は「あれば返す、なければブロックを実行して保存」を1回で行います。

```ruby
# ブロックの結果を12時間キャッシュ
Rails.cache.fetch("stats/active_users", expires_in: 12.hours) do
  User.where(active: true).count   # 重いクエリ
end

Rails.cache.write("key", value, expires_in: 5.minutes)
Rails.cache.read("key")
Rails.cache.delete("key")
```

**🎯 Django:** キャッシュは `django.core.cache` の低レベルAPIで読み書きします。

```python
from django.core.cache import cache

# fetch 相当（get_or_set）
stats = cache.get_or_set(
    "stats/active_users",
    lambda: User.objects.filter(active=True).count(),
    timeout=60 * 60 * 12,   # 秒指定（expires_in 相当）
)

cache.set("key", value, timeout=300)
cache.get("key")
cache.delete("key")
```

フラグメントキャッシュはテンプレートの `{% cache 3600 key %}…{% endcache %}`、ビュー単位は `@cache_page` デコレータで行います。`cache product` のような updated_at 連動の自動失効はなく、キーは自分で設計します。

### キャッシュストアの選択

```ruby
# config/environments/production.rb
config.cache_store = :solid_cache_store   # Rails 8標準（DBベース）
# config.cache_store = :redis_cache_store, { url: ENV["REDIS_URL"] }
# config.cache_store = :memory_store, { size: 64.megabytes }
```

**🎯 Django:** キャッシュバックエンドは `settings.py` の `CACHES` で選びます。

```python
# settings.py
CACHES = {
    "default": {
        "BACKEND": "django.core.cache.backends.redis.RedisCache",  # locmem / memcached / db も可
        "LOCATION": os.environ["REDIS_URL"],
    },
}
```

solid_cache 相当のDB標準はありませんが、`db.DatabaseCache`（要 `createcachetable`）や `locmem`（memory_store 相当）が選べます。

| ストア | 特徴 |
| --- | --- |
| `:memory_store` | プロセス内メモリ。単一プロセス開発向け。プロセス間で共有されない |
| `:file_store` | ファイル。手軽だが低速 |
| `:redis_cache_store` | Redis。複数サーバで共有。要Redis |
| `:solid_cache_store` | **Rails 8標準**。DB（RDB）ベースでRedis不要。大容量に強い |

**Solid Cache（Rails 8標準）** はディスク（DB）を使うため、メモリキャッシュより大量のデータを安価に保持できます。

## 9. credentials と環境変数

APIキーやパスワードなどの秘匿情報は、コードに直書きせず暗号化された credentials か環境変数で管理します。

### Rails credentials

`config/credentials.yml.enc`（暗号化済み）を `config/master.key` で復号します。**master.keyはgit管理しない**（`.gitignore` 済み）ことが必須です。

```bash
# 編集（エディタが開く。保存すると再暗号化される）
EDITOR="code --wait" rails credentials:edit

# 環境ごとに分ける場合
rails credentials:edit --environment production
# => config/credentials/production.yml.enc と production.key を生成
```

```yaml
# credentials:edit で開くファイルの中身（平文で編集）
aws:
  access_key_id: AKIA...
  secret_access_key: xxxx
sendgrid:
  api_key: SG.xxxx
```

```ruby
# 読み出し。dig はキーが無くてもエラーにならず nil を返す（安全）
Rails.application.credentials.dig(:aws, :access_key_id)
Rails.application.credentials.aws[:secret_access_key]  # キーが無いと例外
```

### 環境変数

インフラ側（コンテナ・PaaS）から渡す値は環境変数で扱います。開発では `dotenv-rails` gem で `.env` を読み込むことが多いです。

```ruby
ENV["DATABASE_URL"]
ENV.fetch("REDIS_URL", "redis://localhost:6379")  # 未設定時のデフォルト
```

**🎯 Django:** 秘密情報は基本的に環境変数から読みます（django-environ / python-decouple が定番）。

```python
# settings.py
import environ
env = environ.Env()
SECRET_KEY = env("SECRET_KEY")
DATABASE_URL = env("DATABASE_URL", default="postgres://localhost/app")
```

`credentials.yml.enc` のような暗号化された秘密管理は標準になく、暗号化は外部（Vault / クラウドのSecret Manager）に委ねるのが一般的です。

| 方式 | 向いている用途 |
| --- | --- |
| credentials | アプリに紐づく秘密情報。バージョン管理したい（暗号化して） |
| 環境変数 | デプロイ環境ごとに変わる値、インフラから注入する値 |

**本番の鍵の渡し方:** `master.key` の中身を環境変数 `RAILS_MASTER_KEY` として渡すと、ファイルを置かずに復号できます（コンテナデプロイで一般的）。

## 10. デプロイ

本番稼働に必要な要素を押さえます。RailsはPumaで動かし、静的アセットは事前コンパイルし、秘密鍵を安全に渡します。

### アセットのプリコンパイル

```bash
# JS/CSS/画像を public/assets 以下に事前ビルドする
RAILS_ENV=production bin/rails assets:precompile
```

**🎯 Django:** 静的ファイルは `collectstatic` で `STATIC_ROOT` に集約します。

```bash
python manage.py collectstatic --noinput
```

配信は WhiteNoise（アプリ内で配信）や Nginx / CDN を使います。JS/CSSのバンドルはDjango標準に含まれず、必要なら vite / webpack 等を別途組み合わせます。

### アプリケーションサーバ（Puma）

Railsの標準Webサーバは Puma（マルチスレッド）です。ワーカー数・スレッド数を環境変数で調整します。

```ruby
# config/puma.rb（抜粋）
threads_count = ENV.fetch("RAILS_MAX_THREADS", 5)
threads threads_count, threads_count
port ENV.fetch("PORT", 3000)
workers ENV.fetch("WEB_CONCURRENCY", 2)   # プロセス数（マルチコア活用）
```

**🎯 Django:** Pumaに相当する標準サーバはなく、WSGI/ASGIサーバを選びます。

```bash
# WSGI（同期）は gunicorn
gunicorn myproject.wsgi:application --workers 3 --threads 2 --bind 0.0.0.0:8000

# ASGI（Channels等の非同期）は uvicorn / daphne
uvicorn myproject.asgi:application --host 0.0.0.0 --port 8000
```

同期処理は gunicorn、WebSocket等の非同期は uvicorn / daphne を使い分けます。

### 本番で必須の環境変数

| 変数 | 役割 |
| --- | --- |
| `RAILS_ENV=production` | 本番モードで起動 |
| `SECRET_KEY_BASE` | セッション・暗号化の署名鍵。**必須・秘匿** |
| `RAILS_MASTER_KEY` | credentials復号鍵（ファイルの代替） |
| `DATABASE_URL` | 接続先DB |
| `RAILS_LOG_TO_STDOUT` | ログを標準出力へ（コンテナ運用で有用） |
| `RAILS_SERVE_STATIC_FILES` | Railsから静的ファイルを配信する場合に設定 |

```bash
# SECRET_KEY_BASE の生成
bin/rails secret
```

**🎯 Django:** 本番設定は `settings.py` と環境変数で行います。

```python
# settings.py
SECRET_KEY = os.environ["SECRET_KEY"]   # SECRET_KEY_BASE 相当
DEBUG = False                            # RAILS_ENV=production 相当
ALLOWED_HOSTS = ["example.com"]
```

> 起動時は `DJANGO_SETTINGS_MODULE=myproject.settings.production` で設定モジュールを選びます（`RAILS_ENV` の切替に相当）。

`SECRET_KEY_BASE` ↔ `SECRET_KEY`、`RAILS_ENV=production` ↔ `DEBUG=False`（+ `DJANGO_SETTINGS_MODULE`）が対応します。

### Kamal（Rails 8標準のデプロイツール）

**Kamal** はRails 8に同梱される、自前サーバ（VPS等）やクラウドへコンテナをデプロイするツールです。Dockerイメージをビルドしてサーバへ配布し、ゼロダウンタイムで切り替えます。PaaSに縛られず、SSHでアクセスできるサーバがあれば動きます。

```yaml
# config/deploy.yml（抜粋）
service: my_app
image: myuser/my_app
servers:
  web:
    - 192.168.0.1
registry:
  username: myuser
  password:
    - KAMAL_REGISTRY_PASSWORD    # 環境変数から
env:
  secret:
    - RAILS_MASTER_KEY
```

```bash
# 初回セットアップ（サーバ準備＋初回デプロイ）
kamal setup

# 以降のデプロイ
kamal deploy

# ログ確認・ロールバック
kamal app logs
kamal rollback
```

### デプロイ前チェックリスト

- `RAILS_ENV=production bin/rails assets:precompile` が通る
- `SECRET_KEY_BASE` / `RAILS_MASTER_KEY` を安全に注入している
- `bin/rails db:migrate` を本番DBに対して実行する手順がある
- Solid Queue / Solid Cache / Solid Cable 用のテーブルをマイグレート済み（Rails 8で採用時）
- ジョブワーカー（`bin/jobs` またはSidekiq）を別プロセスとして起動している
- ログを標準出力に出し、監視・エラー通知を設定している
